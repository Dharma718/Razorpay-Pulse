# Razorpay Pulse — AI Payment Reliability & Revenue Intelligence Agent

**Razorpay AI Buildathon — Track 03: AI Revenue Recovery**

> Aggregate payment success rate dashboards hide the incidents that actually cost the most. A single bank or processor quietly failing at 40% instead of 92% barely moves an overall number — but it's a very real, very concentrated pile of lost revenue. Pulse is built specifically to catch, explain, and act on exactly that blind spot.

## Positioning — honestly, against what Razorpay already ships

Before building this, we checked what Razorpay already has in production, because pretending otherwise would be dishonest and easy for a judge to catch:

- **RAY Concierge** already monitors 20+ critical payment metrics and alerts merchants before failures escalate.
- **Agent Studio** (launched March 2026, built on Anthropic's Claude Agent SDK) already ships production agents for abandoned cart recovery, dispute response, subscription recovery, cashflow forecasting, and settlement insights.

Pulse does not duplicate any of these. It's built for the specific gap between "the dashboard looks mostly fine" and "a specific bank/processor/region is quietly failing far worse than the aggregate suggests." Pulse's job is to:

1. **Detect** a localized anomaly even when it's diluted out of the overall metric
2. **Investigate** it with evidence — which method, which provider, which region, which error code — the same way a human analyst would drill down
3. **Quantify** the actual revenue at risk, with a hedged (not inflated) recoverable estimate
4. **Recommend** a bounded action, gated by both confidence AND risk — never one alone
5. **Learn** from the outcome, so the next similar incident has precedent to cite

## Important honesty note

All transaction data in this project is **synthetic and simulated** — generated by a Node.js traffic simulator with configurable baselines per payment method, provider, and region. This is clearly not real Razorpay production data, and the project does not claim otherwise anywhere in its UI or code. Revenue figures are labeled "estimated" and "recoverable estimate," never "revenue saved," because in a simulation nothing was actually saved — the goal is to demonstrate the reasoning and decision architecture, not to fabricate results.

## Architecture

```
backend/
  config.js        Baselines, thresholds, and the 4 injectable incident scenarios
  simulator.js      Generates realistic tick-by-tick transaction traffic
  investigate.js    Root-cause drill-down — region → method → provider → error code,
                     purely from observable deviations (never peeks at ground truth)
  revenue.js        Revenue-at-risk quantification with hedged recovery probability
  planner.js        Guardrails — confidence + risk jointly gate autonomy
  memory.js         Persists resolved incidents to disk for future precedent
  gemini.js         Narrative generation only — never touches the diagnosis or action
  server.js         Tick loop orchestration + Express API
  pulse.test.js     Unit tests covering detection, revenue math, and guardrail logic

frontend/           Vanilla HTML/CSS/JS dashboard — Command Center, live investigation
                     panel, revenue impact, guardrails explainer, incident memory
```

**Data flow:** every ~2.5 seconds, the simulator generates one "tick" of transaction volume across 4 payment methods, 10 providers, and 4 regions. The detector checks overall, per-method, and per-region deviations against baselines (checking sub-dimensions matters — a single-bank incident can be too diluted to show up in the overall number alone). Once an anomaly persists for 2 consecutive ticks, the investigation engine drills down and classifies the pattern into one of: `bank_degradation`, `card_processor`, `merchant_infra`, or `regional_network` — purely from evidence, never by looking at which scenario was actually injected. The revenue engine quantifies exposure, the planner decides the autonomy tier, and the outcome is persisted to `backend/incident-memory.json` once resolved.

## Guardrails (the part that should hold up under questioning)

| Confidence | Risk | Result |
|---|---|---|
| < 60% | any | **Investigate further** — never guesses, flags for manual review |
| ≥ 85% | low | **Auto** — acts without waiting |
| any | medium/high (but auto-approvable type) | **Approval required** — human must click approve |
| any | merchant-side pattern | **Human only, always** — never automated regardless of confidence |

The LLM (Gemini) is used **only** to turn structured evidence into a plain-English narrative and customer notices. The category, confidence score, and action decision are 100% deterministic code — auditable by a human, not dependent on an LLM call that could hallucinate.

## Setup

```bash
cd backend
npm install
cp .env.example .env    # optionally add GEMINI_API_KEY for narrative generation
node server.js
```

Open `http://localhost:5000`. The simulation starts running immediately in a healthy state.

**Note on Gemini API keys:** Google is currently mid-rollout on a new `AQ.`-prefixed API key format alongside the older `AIzaSy` format, and different accounts/transports handle this inconsistently as of mid-2026 (see Google's own AI Developers Forum for many open threads on this). `gemini.js` tries both known auth transport methods (query parameter and header) automatically and falls back gracefully to rule-based output if neither works — this is a known external inconsistency on Google's side, not something fixable purely in application code, and it doesn't block any core functionality since Gemini is a narrative enhancement, not a dependency.

## Features added beyond the core buildathon requirement

- **Manual dismiss, not auto-clear.** A resolved incident stays on screen indefinitely — with a full "Successfully Resolved" summary (what happened, why, how it was fixed, and the outcome) — until you click **Dismiss**. Nothing disappears on a timer.
- **Free-form issue reporting.** Not every real-world problem fits a preset scenario. Below the scenario buttons, you can type your own issue description (optionally speak it via the browser's built-in speech recognition, or attach a screenshot). Gemini interprets it into the same category system — or a simple keyword-based fallback does, if Gemini isn't configured — and the **same deterministic guardrails** in `planner.js` decide the action. No revenue figure is fabricated for these, since there's no live simulated traffic behind a typed report to measure exposure from.
- **Clickable incident history.** Every entry in Incident Memory opens a full detail view — evidence, confidence, audit trail, before/after rates, and revenue figures — not just a one-line summary. Each entry also shows the full date and time it was resolved, not just a time stamp.
- **Clear History** button to wipe all incident memory at once, plus a small **×** on each individual entry to delete just that one — independent of resetting the live simulation.
- Clicking "Razorpay Pulse" in the top nav scrolls back to the top of the page.

## Authentication

This is a real fintech-style product surface, not an open demo page — payment data, incident details, and actions require signing in.

**First time running it:** open the app, and since no account exists yet, you'll be prompted to create one (email, password, confirm password — with a show/hide toggle on both password fields). This is a one-time setup, not a full signup system; there's exactly one owner account per deployment, stored locally as a salted hash (never plaintext) in `backend/owner-credentials.json` (gitignored).

**After that:** you'll see a normal sign-in form, plus a **"Continue with Demo Account"** button — this is what you'd hand to a recruiter or evaluator. It requires no credentials and grants full read/write access to try every feature, including clearing or deleting incident history, so nothing is held back from an evaluator. The real distinction is session length: demo sessions expire after 2 hours, owner sessions last 7 days.

Sessions are JWTs in an httpOnly cookie — owner sessions last 7 days, demo sessions 2 hours. Set `SESSION_SECRET` in `.env` to a long random string if you want sessions to survive a server restart; if left blank, a random one is generated each run (meaning everyone gets signed out on restart — fine for a demo, worth setting properly if you deploy this somewhere persistent).

## Running the demo

1. Open the dashboard and let it run for a few seconds in the healthy state.
2. Click one of the four **"Inject an incident"** buttons in the Command Center.
3. Watch the health pill change, the method-health bars shift, and — within ~5-10 seconds — the Investigation panel populate with evidence, confidence, and a revenue estimate.
4. Depending on the scenario:
   - **Bank/Processor degradation** → click **Approve action** to trigger simulated recovery.
   - **Merchant-side regression** → only a **"I've applied a manual fix"** button appears — this is intentional, demonstrating the guardrail that refuses to automate merchant-side fixes.
   - **Regional network issue** → this one auto-applies immediately (high confidence, low risk) — no button needed.
5. Watch the success rate climb back to baseline and the incident move into **Incident Memory** at the bottom.
6. Trigger the same scenario type again — the Investigation panel will now cite the prior incident's outcome as precedent.

## Evaluation

```bash
cd backend
npm run evaluate
```

This runs 50 independent trials per incident type (200 total) and measures how often the root-cause classifier correctly identifies the injected scenario — again, purely from evidence, never by peeking at ground truth. Measured result on this codebase:

```
Scenario             Accuracy     Avg Confidence (correct)
--------------------------------------------------------------------------------
bank_degradation     100.0%       90.0
merchant_infra       100.0%       90.0
regional_network     100.0%       90.0
card_processor       100.0%       90.0
--------------------------------------------------------------------------------
Overall accuracy: 100.0% (200/200 trials)
```

**Honest caveat:** confidence saturates at 90% here because these test scenarios have a strong, cleanly-isolated signal (the confidence formula caps once the isolation ratio maxes out). A noisier or overlapping real-world incident — two things degrading at once, or a smaller effect size — would be expected to produce lower, more varied confidence, which is exactly the case the `< 60% → investigate further` guardrail exists for. This benchmark validates the classifier's logic is correct on clean signals; it isn't a claim that real-world confidence will always be this high.

## What's genuinely real vs. simulated

- **Real:** the statistical anomaly detection, the evidence-based root-cause classification logic, the revenue math, the guardrail/autonomy rules, and the incident-memory learning loop — all deterministic, tested code.
- **Simulated:** the transaction data itself (no real Razorpay account data), and "recovery" (the success rate is nudged back toward baseline by the simulator when an action is approved, representing what the action would be expected to achieve — it isn't calling real bank APIs).

This distinction is worth stating explicitly and confidently in a pitch — it shows judgment about what to fake and what not to.
